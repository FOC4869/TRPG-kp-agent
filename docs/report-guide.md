# 写报告时可以直接用的材料

本文件帮助六位组员分头写同一版项目。描述的是当前主版本，原始实验材料见 [实验索引](evaluation/README.md)。
下面提供结构和可改写的段落，不替组员填写真实姓名、个人贡献或没有进行过的实验。

## 一句话介绍

我们做了一个面向单玩家 COC 调查故事的 AI KP：玩家自由描述行动，单 Agent 结合当前公开进度理解意图，
通过 RAG 查询规则，再调用确定工具完成掷骰、物品和角色状态处理，最后根据真实结果进行叙述。

## 可改写的摘要

本项目实现了一个单玩家 COC AI 守秘人系统，以自然语言交互支持原创调查故事。
系统使用 React 和 FastAPI 提供网页界面，以 LangGraph 组织单 Agent 的加载、规划、检索、验证、执行、提交和叙述流程。
本地规则检索提供可追溯依据；角色数值、随机检定、物品与剧情状态由确定工具维护。
系统通过保存请求、出目和提交阶段支持中断恢复，避免重复结算。
当前验证范围为一位可玩角色和三个相连地点，最终后端 223 项离线检查通过，真实 API 主流程 61 项检查及 10 项补测通过。
迭代中发现，结构化输出和真实引用仍不足以保证意图与算术正确，因此增加目标一致性检查、具体追问和确定工具算例。

摘要中的“通过”指已有检查范围，不代表对全部 COC 规则或任意自然表达的正确性保证。

## 方法部分可改写的段落

### 单 Agent 与受控工具

系统只使用一个 AI KP。每轮将当前公开对象、已获得线索、实际库存、人物数值与合法行动列表传给规划步骤。
模型输出结构化意图，而不输出资源增减和出目；程序验证目标、方法、物品与前提后调用确定工具。
执行结果先保存，再交给叙述步骤。对含糊对象，系统直接提出包含对象和候选操作的追问，
而不是靠模型选择另一个合法目标来完成玩家没有授权的行动。

### RAG 与确定计算分工

规则检索基于整理后的 17 个主题，片段带规则书版本、来源和核对页码。
当前网页采用本地关键词检索，并将本轮检索结果及证据编号交给解释步骤。
程序验证引用来自本轮证据，但历史失败说明，引用真实不保证算术正确。
因此，成功等级和奖惩骰的基本算例由已有数值代码生成，模型主要承担意图理解和叙述。

### 保存与恢复

系统将随机结果保存、状态提交与正文完成分成不同阶段。
重复请求沿用原编号与内容，已经提交的行动不再次执行。
网页的 SSE 订阅可以断开，恢复时读取持久检查点，继续未完成的正文。
该设计在单进程、独立 JSON 存档下验证，不声称已解决多服务器部署的一致性问题。

## 结果怎么写才准确

| 可以写 | 不要改写成 |
|---|---|
| 最终后端 223 项离线检查通过 | 223 位用户满意，或 223 条模型输入全对 |
| 最终 API 流程 61 项检查、补测 10 项通过 | 模型准确率 100%，或者正好调用 71 次模型 |
| 最新完整路线 47 次 API，补测 8 次 | 所有测试一共只调用 55 次；实际排障累计是 139 次 |
| 历史同一组 23 例：关键词 14/23，DeepSeek 21/23 | 当前网页版已完成同组准确率复测 |
| 历史定向 4 例：模型原始 3/4，应用保护后 4/4 | 模型本身 4/4，或修复后全部 23 例全对 |
| 页面能看 11 位人物、2 个故事资料 | 11 位人物与两个完整故事都已游玩验收 |
| 使用 LangGraph 编排和 Python 工具 | 已部署多 Agent、MCP 服务器或向量数据库 |
| 规则检索有出处，确定数值由代码产生 | RAG 已消除幻觉，或已完整覆盖全部 COC 规则 |

“不改状态”应具体说明：不推进剧情、不扣资源、不掷骰。
问题与追问仍会保存对话并可能增加版本号，不能把整份存档要求为字节不变。

## 报告中可用的贡献点

这些是本项目实际做出的设计与实现，不应直接写成已经证明普遍优于所有方案的学术创新：

1. 自然语言、规则依据与确定工具结合，并保持剧情资料和规则资料分开。
2. 除了检查工具合法性，还检查玩家明确指定的目标与物品，减少意图被改写。
3. 用公开状态生成建议和场景描述，避免满血仍推荐治疗、用完物品仍称持有等不一致。
4. 用出目日志与提交检查点恢复同一回合，防止网络重发造成重复扣值或发奖励。
5. 把失败记录、原始模型评分和保护后评分一起保留，使迭代结论有出处。

## 讨论与未来工作

当前主要限制是有限规则片段、受控故事与有限语言保护，没有完整战斗、通用施法、多人、账号或正式用户研究。
可讨论的下一步包括：为新故事补结构化行动与结局、给规则检索制作独立标注集、扩大自由表达样本，
以及在固定样本上比较有无检索／保护的结果。它们是未来工作，不是已完成的实验。

如果以后做多 Agent，应先说明它解决了当前单 Agent 的什么实际问题，再比较正确率、调用量和响应时间。
本轮没有多 Agent 对照，不能只根据架构名字声称改进效果。

## 六人如何合并写作

可以按上面章节分工，但最后由一人统一术语与数字。
每位成员填写自己的实际工作、对应文件或提交和验证证据；不要把建议分工当作已经发生的贡献。
Agent＋RAG、规则／保存、前端、实验整理、正文整合、pre 与演示可以作为核对工作范围的六类。

合稿时重点检查：同一处是否混用了 CLI 与网页、旧版与新版、模型与应用、实际随机骰与固定测试骰，
以及“可以查看的资料”与“已经可以游玩的故事”。
