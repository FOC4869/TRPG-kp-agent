# 跑团主持人 Agent — 总体设计（v2.2）

> 更新日期：2026-10-20
> 目标：制作一个跑团守秘人（Keeper）Agent，主目标系统为 **COC 7 版（克苏鲁的呼唤）**，架构规则无关、可迁移到其他系统。

## 需求映射

| 需求 | 对应模块 |
|---|---|
| 1. 导入规则后识别并存储规则 | 规则引擎 |
| 2. 导入模组，以守秘人身份 + NPC 引导玩家 | 模组管理器 + 守秘人编排层 |
| 3. 导入角色卡、存储属性、掷骰判定、同步更新属性 | 角色状态层 + 判定工具（trpg-dice-mcp） |

## 核心思想

**LLM 只负责「叙事、扮演 NPC、决定要不要掷骰」；掷骰与规则判定交给确定性工具，属性增减由自写状态层事务性完成，LLM 永远只读结果、不自己算数字。**

## 关键设计原则

1. **掷骰/判定是确定性工具，LLM 不生成数字**（幻觉是跑团的第一杀手）。
2. **角色属性是单一数据源**：每次检定后由状态层事务性更新，Agent 查库而非从对话历史「回忆」数值。
3. **信息门控**：已揭示线索作为显式状态，未揭示线索对守秘人不可见（不能剧透）。
4. **规则与代码解耦**：具体规则当配置/数据，方便后续换系统（如 D&D）。

## 模块一：规则引擎

两条线并行处理规则书（PDF / Markdown / 文本）：

- **语义检索线（RAG）**：规则书转文本 → 按章节切块 → 向量化入库 → 守秘人遇到不确定规则时检索引用。用于「XX 情况如何判定」这类开放式问题。
- **结构化规则线**：把可机读的硬规则抽取成结构化数据，而不是让 LLM 每次读原文：
  - 技能列表、属性定义、派生值公式（HP = (CON+SIZ)/10，SAN = POW，MP = POW/5 …）
  - 成功等级判定表、奖惩骰规则
  - 伤害骰、理智损失、成长检定、疯狂阈值

> 原则：**能变成公式/表格的规则尽量结构化；只有模糊叙述才走检索。** 结构化部分是判定与状态层的正确性依据。

**实现（`trpg/` 包）**：结构化硬规则在 `rules.py`（派生公式/伤害加值表/移动力/理智阈值/成长/默认技能）；RAG 检索在 `rules_store.py`（切块 + 关键词/向量检索 + JSON 持久化，embedder 可插拔）；种子规则见 `data/rules_core.md`。

**规则更新方式（定案）：方式二 · Markdown 导入 RAG**

1. 把新规则写成 Markdown 或纯文本（**UTF-8**），用 `#`/`##` 标题分章节（标题即检索时的章节标识），参考 `data/rules_core.md`。
2. 文件放进规则目录（如 `data/`，或任意目录）。
3. 导入并检索：

```python
from trpg import RuleStore
store = RuleStore()
store.add_dir("data/")            # 批量导入目录下所有 .md/.txt
store.search("临时疯狂怎么判定")   # 检索引用
```

4. 想长期保存：`store.save("data/rules.json")`，下次 `RuleStore.load("data/rules.json")` 读回。

> 边界：这样导入的规则只进检索库、供守秘人查阅引用，**不被机械执行**；要新增可执行的硬规则（新公式/判定表/阈值）仍须改 `rules.py`。

## 模块二：模组管理器 + 守秘人叙事

模组解析成**场景图 + 一组实体**，而非一坨文本：

- **场景/地点**：名称、描述、可通往哪里、里面有什么
- **NPC**：姓名、身份、性格、知道什么（秘密）、属性/技能值、立场
- **线索**：内容、所在场景、获取条件（检定/搜索/对话）
- **事件/时间线**：触发时机、前置条件
- **遭遇/战斗**、**结局条件**

守秘人在游戏期间维护**会话状态**：

- 当前位置、已访问场景
- **已揭示线索集合**（信息门控的关键）
- NPC 状态（存活/态度/是否已给出某线索）
- 时间线进度

## 模块三：角色 + 骰子引擎（方案 A）

拆成**自写状态层** + **外部判定工具**两部分：

```
┌────────────────────────────────────────────────┐
│  自写：角色卡状态层（单一数据源）                  │
│   属性/派生/技能/HP/SAN 存取 · 事务更新 · 存档      │
│   决定「掷什么」→ 组织检定请求 → 接收结果 → 落库    │
└───────────────────┬────────────────────────────┘
                    │ MCP 工具调用
┌───────────────────▼────────────────────────────┐
│  套用：trpg-dice-mcp（Komeiji-Shiki）            │
│   暴露 roll_check：COC 7e 检定 / 奖惩骰 / 对抗检定   │
│   只负责「掷出结果 + 成功等级」，不管状态            │
└────────────────────────────────────────────────┘
```

- **自写状态层负责**：角色卡存取、派生值计算、HP/SAN 事务更新、成长检定触发、存档。它是单一数据源，Agent 读属性永远查这里。
- **trpg-dice-mcp 负责**：COC 7e 的 `roll_check` 判定（奖惩骰、对抗检定），以 MCP server 形式挂载，守秘人 Agent 通过 MCP 工具调用，零改造接入。
- 链接：<https://glama.ai/mcp/servers/Komeiji-Shiki/trpg-dice-mcp>

**角色卡数据结构：**

```
角色 {
  id, 名称,
  属性: { 力量, 体质, 敏捷, 外貌, 意志, 智力, 体型, 教育 },
  派生: { HP, SAN, 幸运, MP, 移动力, 伤害加值 },
  技能: { 侦查: 60, 聆听: 45, ... },
  状态: { 受伤, 临时疯狂, ... }
}
```

**对外暴露给 Agent 的工具（接口不变，内部改为调 MCP）：**

| 工具 | 作用 | 实现 |
|---|---|---|
| `skill_check(角色, 技能, 难度, 奖惩骰)` | 技能/属性检定 | 组织请求 → 调 MCP → 返回成功等级 |
| `apply_damage(角色, 数值)` | 扣 HP，处理濒死/死亡 | 自写层更新 |
| `san_loss(角色, 数值)` | 扣 SAN，触发疯狂判定 | 自写层更新 |
| `improve_check(角色, 技能)` | 成长检定 | 自写层更新 |

**房规导入接口（判定工具层已实现，[trpg/](trpg/) 包）：**

判定逻辑已移植为 Python 包 `trpg/`（零第三方依赖，纯标准库），内置标准规则书，房规可通过 `CocHouseRules` 导入覆盖，未指定字段自动回退标准：

| 旋钮 | 可选值 | 缺省（标准规则书） |
|---|---|---|
| `critical` 大成功 | `roll_1` / `roll_le_5` / `roll_le_skill_div_5` | `roll_1`（出目 01） |
| `fumble` 大失败 | `standard` / `roll_ge_96` / `roll_100` | `standard` |
| `extreme_divisor` 极难 | 整数 | 5 |
| `hard_divisor` 困难 | 整数 | 2 |

导入接口：`CocHouseRules.from_dict` / `from_json` / `from_json_file`；`house_rules=None` 即标准规则书。房规 JSON 只写需覆盖的字段：

```json
{ "critical": "roll_le_5", "fumble": "roll_ge_96" }
```

> 注意：即使套用了开源判定引擎，「属性持久化与事务更新」这一层仍必须自写——开源工具只负责「掷出结果」，不负责状态管理，而这恰恰是本项目最不能错、最容易漂移的部分。

## 多角色管理与切换（Roster）

单张卡靠 `load_character_from_xlsx` 导入即可；一场跑团通常有 2+ 玩家、还要能中途加人/换人，所以状态层之上再加一层**花名册 Roster**：一队角色 + 一个「当前操作对象」指针。切换角色 = 改指针，不改任何角色数据。

**三层结构**

| 层 | 职责 |
|---|---|
| 导入层 | Excel → `Character`（`excel_import.py`） |
| 容器层 | `Roster`：`dict[id, Character]` + `active_id` 指针 |
| 存档层 | 整队 + 各自当前 HP/SAN 落盘到一个目录 |

**稳定身份 id**：从 Excel 导入用**文件名 stem**（稳定、可读、同文件重导 = 覆盖更新）；手工 `add` 用名字 slug（ASCII 化，冲突追加 `-2`/`-3`，纯中文回退 `char`）。

**接口**

```python
r = Roster()
r.import_dir("characters/")            # 批量导入目录下所有 xlsx，激活第一张
r.import_xlsx("characters/Alice.xlsx") # 导入一张新卡并激活
r.switch("alice")                      # 切换当前操作角色
r.active                               # 当前 Character（无则 None）
r.list()                               # [(id, 名字), ...]，按加入顺序
r.save("saves/session-001")            # 落盘整队
r = Roster.load("saves/session-001")   # 恢复整队 + 谁在操作
```

**存档布局**

```
characters/            # 只读导入源（Excel）
  Richard….xlsx  Alice….xlsx
saves/session-001/     # 运行态
  roster.json          # {"active_id": "...", "order": [...]}
  <id>.json            # 每个角色当前 HP/SAN（复用 Character.to_dict）
```

**更换/导入流程**

- **A · 开局导入一队**：玩家把角色卡 xlsx 丢进 `characters/` → `Roster.import_dir("characters/")` 扫描全部 xlsx、按文件名 stem 登记、激活第一张 → `list()` 确认成员齐全。
- **B · 中途加入新角色卡**：新卡放进 `characters/` → `r.import_xlsx(path)` 读卡、按文件名生成 id、登记并激活为新当前角色 → 旧角色 HP/SAN 保持不动。同名文件重导 = 覆盖更新该卡（从 Excel 重读，丢弃会话内改动）。
- **C · 切换当前操作角色**：`r.switch(id)`（id 用 `list()` 查得）→ 此后 `r.active.check("侦查")` / `apply_damage` / `san_loss` 都落在该角色上，其余角色不受影响。
- **D · 退出重进恢复**：`r.save(dir)` 写 `roster.json` + 每角色 `<id>.json`；下次 `Roster.load(dir)` 恢复全队 + 最后操作的角色（`active_id` 随存）。

> 多玩家时「玩家→角色」绑定放会话层（第 5 步），守秘人按 `roster.get(player_id)` 取角色；`active` 只是单人/CLI 的便捷指针。

## 编排框架选型（LangGraph + MCP）

- **用 LangGraph 做守秘人编排**：
  - `StateGraph` + checkpointing 承载会话状态持久化（正是「单一数据源」需要的落点）；
  - `bind_tools` + `ToolNode` + `tools_condition` 承载工具调用（骰子/角色工具）；
  - `interrupt` 承载等待玩家输入（human-in-the-loop），契合跑团回合制节奏；
  - 未来想给不同 NPC 拆子 agent 时，用图的组合能力扩展。
- **MCP 接入**：用 [langchain-mcp-adapters](https://pypi.org/project/langchain-mcp-adapters/)（[GitHub](https://github.com/ibusybox/langchain-mcp-adapters)）的 `MultiServerMCPClient` / `load_mcp_tools`，把 MCP server 的工具直接加载进 LangGraph。
- **说明**：LangGraph 非必须——手写「LLM 循环 + 工具调用」也能跑，但它省掉状态持久化/断点续跑/多 agent 组合的样板代码，故推荐。

## 判定工具：跨语言与移植策略

- **前提**：MCP 是跨语言协议（JSON-RPC over stdio/HTTP），trpg-dice-mcp 虽是 TypeScript，Python 端仍可直接通过 `StdioServerParameters(command="npx"/"node", ...)` 拉起并调用，**无需改写**——这是「方案 A」的字面含义。
- **但可移植**：`roll_check` 的判定逻辑（COC 7e 成功等级、奖惩骰、对抗检定）是自包含小逻辑（几十到一两百行），可参考 TS 源码改写成 Python。
- **移植要点**：读 TS 源码吃透边界语义——尤其 `00` 当作 100、奖惩骰的取十位规则、大成功/极难/困难的阈值取整方式——然后 Python 重写 + 单元测试，并对拍 TS 输出做 golden test（固定输入比对两边结果）。
- **策略（两步走）**：
  1. 起步先**直接连 TS 版 MCP** 跑通语义，把 TS 当「规格说明书」核对成功等级是否符合房规；
  2. 语义确认后**移植成 Python 内嵌**进状态层——状态层要「检定 → 扣 HP/SAN → 成长检定」紧耦合判定，内嵌后无跨进程边界、可确定性测试、单代码库更好维护。

## 前端选型（多玩家）

- **目标**：支持 2+ 玩家同场，核心需求是**实时广播**（玩家行动 / 守秘人叙述实时推送给所有玩家），需要 WebSocket 双向推送。
- **选择**：**React + FastAPI + WebSocket**。FastAPI 原生支持 WebSocket，自然承载房间/会话管理、玩家身份、权限（守秘人 vs 玩家视角）。
- **不选 Streamlit 的原因**：其执行模型是「脚本重跑 + `st.session_state` 每会话隔离」，多用户并发实时同步要做大量 hack（外部状态 + 手动轮询/推送），适合单人 demo/原型，不适合多玩家。
- **可选**：若只想快速验证守秘人后端逻辑，可先用 Streamlit 搭一次性单人原型，验证后再上正式 React 前端——但别指望它撑多玩家。

## 数据模型

```
规则库(向量) : 规则原文 chunks + 引用来源

模组(结构化)  : 场景[]  NPC[]  线索[]  事件[]  遭遇[]  结局条件

骰子日志       : 谁·何时·掷什么·MCP结果·触发什么属性变化
```

## 技术选型

- **LLM 编排框架**：LangGraph（详见「编排框架选型」）。
- **判定工具**：已移植为 Python 包 `trpg/`（`dice`/`house_rules`/`check`/`character`/`excel_import`/`roster`），标准规则书 + 房规导入 + 角色卡状态层 + 多角色花名册；原 TS 版 trpg-dice-mcp 可作 MCP 直接连（详见「判定工具」）。
- **前端**：React + FastAPI + WebSocket（详见「前端选型」）。
- **向量库**：规则/模组检索（SQLite + embedding，或 chroma/FAISS）。
- **结构化存储**：角色、会话状态、模组解析结果用 JSON/SQLite。
- **PDF 解析**：规则书/模组导入用 PDF 转文本工具。
