## 先区分版本和验证范围

- **当前 v2：**一名玩家、一张角色卡、一个 Agent，三个地点、八条线索、四种物品、十七个规则主题。
  本轮主要改 Agent、RAG、场景及现有工具的调用适配；没有重写组员的角色／骰子和数据库底层。
- **v2 已归档验证：**60 项离线测试通过；首轮真实模型规划 21/23，应用侧 21/23；
  修后仅定向四例，原始模型 3/4、应用侧 4/4。首轮 23 例没有完整重跑。
- **评分区别：**`raw_model_plan` 是结构化解析后、应用保护运行前的模型动作；`plan` 是保护后的最终动作。
  格式未解析成功时原始动作为空。程序把错误动作改成追问，不等于模型理解正确。
- **范围区别：**自由表达组使用人工构造的公开进度，只调用规划，不执行这些行动；
  不是随机跑团从头通关。另有少量实际 `KeeperService` 回合，不能代替全剧情实测。
- **历史 v1：**旧书房版本的记录单列在后文，不与 v2 的测试数量、调用次数或改动范围合并。
- **本轮提示与描述检查：**第一阶段的 22 项 `test_guidance_v2.py` 检查已经运行：公开描述修复前 8 项失败，
  修复后 22 项全部通过，均使用临时 SQLite、脚本规划器和预设随机数，没有 API 请求。
  后补 4 项服务集成检查，当前此文件共 26 项。
- **本轮最终验证：**2026-10-21，完整离线测试 **98 项全部通过，0.274 秒**，包含原有 60 项和新增 38 项。
  新增 38 项由提示／描述／服务集成 26 项及语言安全 12 项组成，不能再次相加为更多测试。
  否定、假设／后果提问、规则跟进抢占新行动三类问题均已修，详见第十二至十四项。
- **真实模型限制：**本轮用脚本规划器、关键词 Demo 和假 Responses 验证，真实 API 请求为 0；
  尚未重新验证 DeepSeek 对这些新改动的真实输出，不能把离线通过率当成模型语言表现。

## V2-02：合法动作仍可能不符合玩家意图

| 项目 | 记录 |
|---|---|

| 现象 | 模型输出 `use_item/locker/locker_key`，把玩家点名的站台替换成寄存柜。这组物品与目标在场景中合法，单纯检查“能不能开柜子”无法发现它并非玩家要求。 |

## V2-03：引用正确不代表算例正确

| 项目 | 记录 |
|---|---|
| 日期／版本 | 2026-10-21，v2 实际服务两回合检查及后续数值修复 |
| 发现方式 | 人工阅读真实 `KeeperService` 的规则回答。该轮自动状态／结构检查已经通过。 |
| 现象 | 技能值 55 的回答写出“掷出30，不超过27……就是困难成功”，随后还把 30 当作可通过困难任务的出目；所引 `evidence_id` 确实来自当次检索。 |
| 原因 | 数值说明交给模型自由叙述；当时检查引用、返回结构和资源不变，没有独立校验算术和等级语义。RAG 提供了规则，却不能保证模型正确运用它。 |
| 修改 | 增加只读 `CharacterTools.success_example()`，使用已有 `trpg.check` 判定例子，按实际技能值生成门槛。命中成功等级问题及真实来源后，程序直接输出算例并附当前引用，不经模型再次改写。其他普通叙事和规则主题仍走原来的模型路径。 |
| 验证 | 技能 55 的门槛为 55／27／11；假设出目 30 为常规成功且不能通过困难任务，20 为困难成功，10 为极难成功。修后真实检查六项全部通过，只调用 `plan` 一次，`narrate` 零次；离线测试也覆盖另一项技能、未调用随机数、角色不变和引用来自当前检索。 |
| 限制 | 这是教学用假想出目，不是真实骰子或一次游戏行动。只把成功等级算例收回程序，不代表所有自然语言数字解释都已被程序验证。保留原错误材料，不能把原结构检查的 `passed=true` 当成原回答全部正确。 |

## V2-04：重试、物品与混合效果的一致性保护

这部分包含扩展时发现的风险与回归保护。没有证据表明本轮真实玩家曾被重复扣值或重复发物品，
因此不写成已经发生的线上故障。v1 的重复理智损失历史另见后文。

| 项目 | 记录 |
|---|---|
| 日期／版本 | 2026-10-21，v2 多场景扩展与离线检查；另有少量真实服务证据。 |
| 发现方式 | 检查叙述失败后的恢复路径，以及一次行动包含 SAN、伤害、恢复和 MP 消耗时的边界。 |
| 风险现象 | 工具执行后叙述失败，重试若重新规划／重发奖励，会重复消耗钥匙或重复获得物品。多个效果中后一个失败，若前面已经改了原对象，会出现只扣一半状态。把同一 action 的效果由纯 SAN 改成混合列表，也可能改变随机请求编号。 |
| 原因 | “随机值已保存”“状态已提交”“回复已完成”是不同阶段；仅依赖聊天回复或仅看骰子是否存在，不足以判断是否需要再次结算。 |
| 修改 | 沿用现有保存代码的消息、动作和骰子记录；保存首个计划，提交后的动作直接恢复已保存公开结果。效果先验证并在角色／场景副本结算，成功后统一提交。效果已应用标记随场景快照保存；未提交的旧快照仍可按缓存骰子正确应用一次。同一 action 的效果集合变化会被拒绝。物品与场景进度随同一份状态保存。 |
| 验证 | `test_narration_failure_after_key_reward_reuses_committed_inventory` 模拟发钥匙后叙述失败，恢复后规划调用数不增、保存结果不变、两件奖励各一件、原钥匙已消耗。混合效果重复调用数值不变；后续 MP 消耗失败时原角色和场景不半改，重试复用原骰子；纯 SAN 改混合效果被拒绝。归档日志列出这些测试通过。真实两回合另验证相同消息复用结果、状态不变、续档保留地点和库存。 |
| 限制 | 离线用预设随机数、临时数据库和模拟叙述失败；不等于各种网络、进程崩溃、多进程并发均已穷尽。没有改写数据库底层，也没有多人并发服务验证。 |

| 恢复负数、奇数最大 HP 的重伤边界、成长及高属性伤害表错误 | 旧报告逐项记录修复；来源包括核心规则书对应页码。 | 不等于本次 v2 重写底层，也不等于已经有完整战斗／施法系统。 |
| 检索缓存合法 JSON 但结构损坏、并发保存使用同名临时文件 | 增加缓存结构校验、重建和独立临时文件保护。 | 不能由此推出真实向量服务的检索质量已经验证。 |

v1 报告记载的“270 项测试”和“33 个真实对话检查点”均只属于旧版本。
v2 首轮及本轮新增的安全证据均保存在 `docs/evaluation/`，包中也可直接阅读。
最新结果以“本轮最终结果和可复现方法”为准，不混用历史数量。

## 写进课程报告时可直接采用的结论

1. RAG、结构化输出和合法工具调用能缩小错误范围，但不能保证模型理解或算术一定正确。
2. 应分别报告模型原始结果与程序保护后的结果；g11 是二者不能混计的具体例子。
3. 确定性数值交给既有规则引擎，例子和真实掷骰要明确区分；模型主要承担语言理解与叙述。
4. 重试恢复要区分计划、随机结果、状态提交和回复完成，避免把网络重发变成一次新行动。
5. 建议和公开描述都应结合真实角色状态与已获信息；“工具可调用”不意味着“现在应该推荐调用”。
   相关22项离线检查已通过，模型正文的相同行为还没有本轮真实复测。
6. 所有通过数量都附版本、案例范围和限制；保留错误回答和失败记录，避免只展示成功案例。
